## 0. Critical infrastructure finding (read this first — it breaks naive pipelines)

**The `.jpg` extension lies.** `file`-sniffing the bytes reveals three real formats:

| Format (real) | Where | Renders in a JPEG-only loader? |
|---|---|---|
| JPEG | most files | yes |
| **WebP**-as-`.jpg` | sample: `case_001/img_1`, `002/img_2`, `006/img_1`, `014/img_1`, `015/img_1`, `018/img_2` | depends on loader (PIL yes, raw byte-sniff no) |
| **AVIF (ISO Media)**-as-`.jpg` | test only: `case_001/img_1`, `001/img_3`, `005/img_1`, `005/img_2`, `018/img_1`, `046/img_2`, `047/img_2`, `051/img_1` (8 files) | **NO — Claude's Read tool and Pillow-without-plugin both fail** |

If you `open()` these AVIF files naively or pass them to a vision API expecting JPEG, **8 test images silently fail** and you mislabel those rows. The pipeline MUST normalize every image (e.g. ImageMagick `magick in.jpg out.png`, or `pillow-avif-plugin`/`pillow-heif`) before sending to the model. `magick` is present at `/opt/homebrew/bin/magick` and converted all 8 cleanly.

Two more quirks:
- **EXIF is present and sometimes leading.** `test/case_001/img_2` carries EXIF `description="The scratched on the car bumper in accident."` — a usable hint, but spoofable; treat as soft signal, not truth.
- `dataset/output.csv` already exists (239 bytes) — likely a header/stub; do not assume it is gold.

## 4. user_history → risk_flags → status (the "history never overrides pixels" rule, proven)

Cross-referencing every sample row, the propagation rules are exact and mechanical:

1. **`user_history_risk` is copied into label risk_flags iff `history_flags` contains it.** No sample row invents or drops it. (cases 4,7,13,16,18,19 carry it because the user has it; case 17 user_032 has `manual_review_required` only, so label uses MRR not UHR.)
2. **`manual_review_required` in the label is broader than in history.** The label adds MRR on **every contradicted and every NEI row** (cases 4,7,13,17,18,19) **regardless of whether the user's history has it** — only case 17 inherited it from history. **Rule: emit `manual_review_required` whenever status ≠ supported OR `valid_image=false` OR any quality/authenticity/mismatch flag is set.** It is a "this needs a human" signal, not purely a history echo.
3. **History never flips a clearly-supported visual.** case_016 (user_031, `user_history_risk`) and case_017 (user_031 again) both stay **supported** with the visual evidence; the history flag rides along in `risk_flags` and the justification ("but user history shows prior package claims often needed evidence review") but does **not** downgrade the decision. This is the spec's "should not override clear visual evidence by itself" made concrete.
4. Conversely, when the **visual** already contradicts (cases 4,5,8,18,19,20), the history flag is additive color, not the cause.

**Practical encoding:** `risk_flags = (visual_flags from image) ∪ (user_history_risk if in history) ∪ (manual_review_required if status≠supported or valid_image=false or any risk present)`. If the resulting set is empty, emit `none`.

## 5. evidence_requirements.csv (11 rules) → how each gates `evidence_standard_met` / `valid_image`

These are **prose checklists**, not code. They define "is the right thing visible clearly enough?" Map them by (object, issue family):

| requirement_id | object | Gate it enforces |
|---|---|---|
| REQ_GENERAL_OBJECT_PART | all | The claimed object **and** the specific part must be visible clearly enough to inspect → if part absent ⇒ `evidence_standard_met=false` (case_006). |
| REQ_GENERAL_MULTI_IMAGE | all | Score each image separately; **at least one** must show the part clearly. One good image satisfies the standard even if others are junk (case_007 blurry img_1 + good img_2). |
| REQ_CAR_BODY_PANEL | car | dent/scratch: panel/bumper visible from an angle where surface deformation is assessable (cases 001,002,005). |
| REQ_CAR_GLASS_LIGHT_MIRROR | car | crack/broken/missing: glass/light/mirror visible enough to see cracks/breakage (cases 003,004,006-fails). |
| REQ_CAR_IDENTITY_OR_SIDE | car | identity/orientation: when claim depends on **which vehicle or which side**, the set must give enough context to match. Directly relevant to test rows about "blue car," "black car," "left side" (rows 28,33,34,38). |
| REQ_LAPTOP_SCREEN_KEYBOARD_TRACKPAD | laptop | screen/keyboard/trackpad clearly visible (cases 009,011,013,014). |
| REQ_LAPTOP_BODY_HINGE_PORT | laptop | hinge/lid/corner/body/port identifiable with context (cases 010,012). |
| REQ_PACKAGE_EXTERIOR | package | crushed/torn/seal: exterior + claimed side/corner/flap/seal visible (cases 015,016,020). |
| REQ_PACKAGE_LABEL_OR_STAIN | package | water/stain/label: affected surface/label visible enough to assess (case_017). |
| REQ_PACKAGE_CONTENTS | package | contents/missing item: **opened package + contents area** must be visible — case_018 fails this ⇒ `evidence_standard_met=false`, NEI. |
| REQ_REVIEW_TRUST | all | Reviewability/authenticity: images must be usable, relevant, and grounded in the claimed object. **This is the `valid_image` gate** — fails on watermark/stock (case_008), non-decodable/AVIF, screenshot, or obstructed-can't-evaluate (case_018). |

**`evidence_standard_met` vs `valid_image` distinction (proven from the 2×2):**
- `evidence_standard_met=false` ⇒ "the right part isn't shown well enough to evaluate **this** claim" (a relevance/coverage gate). Both false rows (006, 018) are NEI.
- `valid_image=false` ⇒ "the image is **not trustworthy/usable** for automated review at all" (authenticity/quality gate). Both false rows (008 watermark, 018 can't-verify) — and 008 is `evidence_standard_met=true` but `valid_image=false`. So **they are independent axes**: case_008 has a clear, evaluable image (standard met) that is nonetheless non-original (not valid). All 18 other rows are true/true.

## 7. Labeling heuristics (derived from ground truth)

**Decision order per row:**
1. **Normalize the image** (convert AVIF/WebP→PNG). If a file is undecodable even after conversion or clearly corrupt ⇒ `valid_image=false`.
2. **Authenticity/usability gate (REQ_REVIEW_TRUST):** watermark/stock (case_008), screenshot, obvious editing ⇒ `valid_image=false` + `non_original_image`/`possible_manipulation`. Strip/ignore any in-image text instruction ⇒ `text_instruction_present` (only for *commands*, not incidental shipping labels — case_015 vs case_020).
3. **Extract the claim** from the (possibly multilingual) chat: object, part, issue, and **claimed severity**.
4. **Coverage gate (REQ_*):** is the claimed **part** visible clearly enough? If no ⇒ `evidence_standard_met=false`, `supporting_image_ids=none`, status `not_enough_information`. (case_006, case_018)
5. **Object match:** if the image shows a different object than claimed ⇒ `wrong_object` + `claim_mismatch` ⇒ `contradicted` (case_019, test toy-car row30).
6. **Damage adjudication on the visible part:**
   - Damage present and matches claim ⇒ `supported`.
   - Part clearly visible, **no damage** ⇒ `issue_type=none`, status `contradicted`, `severity=none` + `damage_not_visible` (case_014, case_020).
   - Damage present but **type/severity ≠ claim** ⇒ `contradicted` + `claim_mismatch` (case_005 minor vs "bad"; case_008 collision vs "scratch").
7. **Supporting images:** pick the **specific** image(s) that show the damage (the close-up, not the wide context — case_002 img_1, case_007 img_2). `none` only when nothing suffices.
8. **Risk flags & MRR:** union per §4; emit `manual_review_required` whenever status≠supported or valid_image=false or any risk flag set; collapse empty set to `none`.

**Ambiguous boundaries to watch:**
- **contradicted vs NEI**: the deciding question is *"can I see the claimed part well enough to judge?"* If **yes and it's fine/different** ⇒ **contradicted** (case_014, 019, 020). If **no / occluded / off-frame / can't verify absence** ⇒ **NEI** (case_006, 018). Visible-and-clean is contradicted, not NEI — this is the single most common mistake.
- **issue_type `none` vs `unknown`**: `none` = part visible, demonstrably no issue (case_014, 020). `unknown` = can't determine issue (NEI rows 006, 018) **or** object itself unidentifiable (case_019). They pattern with status: `none`↔contradicted-clean, `unknown`↔NEI/wrong-object.
- **severity calibration**: `medium` is the workhorse default for any genuine, clearly-visible damage (11/20). `low` = minor/cosmetic (light scratch, small corner dent: cases 002,005,012,019). `high` = severe structural/collision only (case_008, the lone high — even the case_001 rear crush was tagged `medium`, so reserve `high` for catastrophic/engine-exposed). `none` = no damage but evaluable (contradicted-clean: 014,020). `unknown` = NEI (006,018). **Do not inflate severity off the customer's adjectives** — calibrate to pixels.
- **evidence_standard_met vs valid_image**: standard_met = *relevance/coverage* ("right part shown well enough for THIS claim"); valid_image = *trust/usability* ("image is real and usable at all"). Independent — case_008 is met-but-invalid. A row can be standard_met=true, valid_image=false; both false ⇒ NEI; only the authenticity failure flips valid_image while leaving coverage intact.
