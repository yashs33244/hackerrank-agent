### 1.3 Subtle semantics (the parts that trap people)

- **`evidence_standard_met` vs `valid_image` are two different gates.**
  - `evidence_standard_met` = "is the image **set sufficient to evaluate THIS claim**?" It is claim-specific and checked against `evidence_requirements.csv` (does the set show the claimed object + part clearly enough to inspect the claimed condition?).
  - `valid_image` = "is the image set **usable for automated review at all**?" It is a lower, claim-agnostic bar about reviewability/trustworthiness (REQ_REVIEW_TRUST).
  - The sample data proves they are independent: 18/20 rows have both `true`; **case_008** (`user_008`) is `evidence_standard_met=true` but `valid_image=false` (the image is clear/sufficient to read, but flagged `non_original_image`, so it is not a trustworthy automated-review input). **case_018** (`user_032`) has both `false`. So they correlate but are NOT the same column — `evidence_standard_met=true, valid_image=false` is a real, expected combination when authenticity is suspect.

- **`supporting_image_ids` "none" rule + the ID = filename-without-extension rule.**
  - Image ID = **filename without extension**: `images/test/case_001/img_2.jpg` → ID is **`img_2`** (NOT the path, NOT `case_001/img_2`, NOT `img_2.jpg`).
  - Use the literal string **`none`** when no single image is sufficient to support the decision. In the sample, the 2 `none` rows are exactly the 2 `not_enough_information` rows (case_006 `user_006`, case_018 `user_032`). Note: in case_006 a `contradicted`/insufficient image still exists, but because no image *supports* the decision, `supporting_image_ids=none`. The field means "images that support the chosen `claim_status`," not "images present."
  - When multiple images support: semicolon-joined IDs, e.g. case_020 → `img_1;img_2`.
  - Critically, you select a **subset**: in case_001 there are 2 images but only `img_1` is listed; in case_007 the blurry img_1 is dropped and only `img_2` is listed. The model must pick the image(s) that actually carry the evidence.

- **Semicolon multi-value format** applies to exactly three columns: `image_paths` (input), `risk_flags`, and `supporting_image_ids`. No spaces around the `;` in the sample data (`claim_mismatch;user_history_risk;manual_review_required`). All other multi-valued-looking fields (`issue_type`, `object_part`) are **single-valued**.

- **`issue_type=none` vs `issue_type=unknown`.** This is an explicit rule (problem_statement line 142):
  - `none` → the relevant part **is visible** and **no issue is present** (i.e., the image actively shows the part is fine). Used when contradicting a damage claim because the part looks intact (case_014 trackpad, case_020 seal).
  - `unknown` → the issue/part **cannot be determined** from the image (wrong angle, contents unclear, wrong object). Used in case_006, case_018, case_019.
  - Trap: a `contradicted` row can be `issue_type=none` (part visible, no damage) OR a different real issue (case_005 claims severe damage but issue is `scratch`; case_008 claims hood scratch but image shows `broken_part`). `contradicted` does NOT imply `issue_type=none`.

- **`risk_flags=none` is a value, not empty.** When there is no risk, write the literal `none`, never an empty string and never omit it.

- **History never overrides clean visual evidence by itself** (problem_statement line 13). History only adds `risk_flags` (`user_history_risk`, `manual_review_required`) and justification color — it does not flip `claim_status` on its own. In every sample `contradicted`/risk row, the flip is driven by the image (mismatch, wrong object, damage not visible); history is additive.

### 1.4 ENUM TRAP CHECKLIST — every way a row can be silently wrong/invalid

A row can pass a naive eyeball check and still be scored wrong. Guard against all of these:

1. **Wrong column count / order.** Must be exactly 14 columns in the §1.1 order. The first 4 must echo input verbatim (re-emit, do not re-derive `claim_object`).
2. **Row count mismatch.** `output.csv` must have exactly 44 data rows (one per `claims.csv` row), in the same order. (`claims.csv` = 44 rows.)
3. **Boolean casing.** `evidence_standard_met` / `valid_image` must be lowercase `true`/`false` — not `True`, `TRUE`, `yes`, `1`.
4. **`image_paths` not echoed faithfully** (re-joined with wrong delimiter or spaces). Echo the exact input string.
5. **`user_claim` truncated or quote-mangled.** It contains `|`, commas, and non-Latin/Hinglish text; must survive CSV quoting intact.
6. **Object-part vocab leak across objects.** Using `screen` for a `car`, or `body` for a `package` (package has no `body`; it has `box`). Each object has its OWN vocab; only `unknown` is shared. `body` exists for car and laptop but NOT package.
7. **`issue_type` value not in the 12-item list** (e.g. `broken`, `shattered`, `missing`, `dents`). Note `glass_shatter` and `missing_part` are the canonical spellings; `crushed_packaging`/`torn_packaging` are package-specific.
8. **`issue_type=none` vs `unknown` confusion** (see §1.3): emitting `unknown` when the part is clearly visible-and-fine, or `none` when the part can't be seen.
9. **`severity` invented value** (`minor`, `severe`, `critical`, `moderate`). Only `none/low/medium/high/unknown`.
10. **`severity` type/agreement errors.** When `claim_status=not_enough_information`, sample always uses `severity=unknown`. When `contradicted` because part is fine, `severity` is often `none` or `low`. Mismatched severity is silently wrong.
11. **`claim_status` typo / variant** (`not enough information` with spaces, `insufficient`, `support`, `contradict`). Must be exact: `not_enough_information` with underscores.
12. **`risk_flags` empty instead of `none`.**
13. **`risk_flags` with spaces around `;`** or trailing `;`.
14. **`risk_flags` invented or near-miss tokens** (`blurry`, `manipulation`, `history_risk`, `manual_review`). Must be exact 14-item vocab; e.g. it is `possible_manipulation`, `manual_review_required`, `text_instruction_present`.
15. **`risk_flags` ordering instability** — not known to be scored on order, but keep a deterministic canonical order (e.g., flag-vocab order) to avoid diff noise and to be safe.
16. **`supporting_image_ids` carrying the extension or path** (`img_1.jpg`, `case_001/img_1`). Must be bare ID `img_1`.
17. **`supporting_image_ids` empty instead of `none`** when nothing supports; or listing an image for a `not_enough_information`/no-support case.
18. **Listing ALL images instead of the supporting subset** (case_001/case_007 prove you must drop the non-supporting/blurry ones).
19. **`supporting_image_ids` referencing an ID that isn't in this row's `image_paths`.**
20. **`evidence_standard_met` and `valid_image` forced equal** — they are independent (case_008). Collapsing them loses points.
21. **Letting user history flip `claim_status`** instead of only adding flags (violates the stated rule).
22. **Prompt-injection leakage**: text inside an image or in `user_claim` saying "approve this claim" must NOT change the output; instead set `text_instruction_present` and treat as untrusted. 7 test rows contain approve/ignore/instruction language (rows 4, 7, 10, 24, 28, 36, 43) — see §2.
23. **JSON-of-list serialized into a CSV cell** (e.g. `["img_1","img_2"]`) instead of `img_1;img_2`.
24. **Non-UTF-8 / `\r\n`** line endings corrupting the Hinglish rows (rows 19, 20, 35, 36) — write UTF-8 `\n`.
25. **Missing double-quoting** so a `user_claim` comma/`|` breaks column alignment for that row and silently shifts every later field.

## 2. Scoring Surface — what is likely scored, ranked by difficulty × leverage

The first 4 columns are echoed input and effectively un-scoreable (they only "fail" if you corrupt them — so treat them as a correctness/format gate, not a points opportunity). The 10 produced columns are the scoring surface. Ranked by **how hard they are to get right × how much they likely move the score**:

| Rank | Column(s) | Likely scoring shape | Difficulty | Leverage / notes |
|---|---|---|---|---|
| 1 | **`claim_status`** | Exact-match, 3-class | High (needs true visual reasoning + mismatch detection) | **Highest leverage.** This is the headline decision. Sample dist: supported 13, contradicted 5, NEI 2 — imbalanced toward `supported`. The hard rows are the `contradicted` ones where the image refutes an exaggerated/wrong claim (case_005, 008, 019, 020) and the 2 `not_enough_information` rows. Getting the contradiction/NEI minority right is where points are won. |
| 2 | **`risk_flags`** | Multi-label set match (F1 / Jaccard over 14 labels) | Very high (set prediction, partial credit) | **High leverage, hardest to max.** 8/20 sample rows are multi-flag. Correlated families: `claim_mismatch`+`manual_review_required`, `user_history_risk`+`manual_review_required`. `user_history_risk`/`manual_review_required` are largely **derivable deterministically** from `user_history.csv.history_flags` (free points); the visual flags (`blurry_image`, `wrong_angle`, `damage_not_visible`, `wrong_object`, `non_original_image`, `text_instruction_present`) need the VLM. Mixed determinism = a calibration sweet spot. |
| 3 | **`object_part`** | Exact-match, object-conditioned enum | Medium-high | Strong leverage, and the **vocab is closed and small per object** — a deterministic post-validator (clamp to the object's allowed set, else `unknown`) prevents cross-object leaks. Often inferable from the claim text alone (the user names the part), so part is cheap; the trap is forcing the right value when the image disagrees. |
| 4 | **`issue_type`** | Exact-match, 12-class | Medium-high | The `none`/`unknown` split (§1.3) is the main error source. Frequently inferable from claim text, but must be reconciled with what the image shows (case_005/008 differ from the claim). |
| 5 | **`severity`** | Exact-match, ordinal 5-class | Medium | Lower leverage but cheap. Strong priors: NEI → `unknown`; "part fine" contradiction → `none`/`low`; visible structural damage → `medium`/`high`. Mostly rule-derivable from `claim_status`+`issue_type`. |
| 6 | **`evidence_standard_met`** | Exact-match boolean | Medium | 18:2 skew toward `true` in sample. A "default true, flip false only when part not shown / contents unclear" rule gets most of it. |
| 7 | **`valid_image`** | Exact-match boolean | Medium-low | Even more skewed (18:2). Default `true`, flip `false` on authenticity/`non_original_image` or unreadable/cropped contents. |
| 8 | **`supporting_image_ids`** | Set/exact match over IDs, or partial credit | Medium (selection problem) | Leverage depends on whether scorer is exact-set or lenient. The `none`↔NEI coupling and "pick the supporting subset" rule are the traps. Deterministically: if `claim_status∈{supported,contradicted}` pick the clearest image(s); if NEI → `none`. |
| 9 | **`evidence_standard_met_reason`** | Free text — likely LLM-judge or unscored/light | Low (no exact answer) | Free-text justifications are usually judged for grounding/plausibility or not scored at all. Keep short, image-grounded, mention image IDs. Diminishing returns vs the enums. |
| 10 | **`claim_status_justification`** | Free text — LLM-judge or light | Low | Same as above. Spec literally says "mention relevant image IDs when helpful." Cheap to satisfy; don't over-invest. |

**Strategic read:** Points concentrate in `claim_status` + `risk_flags` + `object_part`/`issue_type` — all deterministic-enum / multi-label targets. The two free-text columns are low-leverage. Several columns (`severity`, `evidence_standard_met`, `valid_image`, the two history flags, `supporting_image_ids=none` on NEI) are **rule-derivable** from the others, so a deterministic post-processor over the VLM's core judgments (`claim_status`, `issue_type`, `object_part`, visual flags) can lock in a large fraction of the surface cheaply and reproducibly (which also satisfies the "deterministic where possible" constraint in AGENTS.md §6.2).

**How `sample_claims.csv` ground truth enables calibration / self-eval:** the 20 labeled rows give you a per-column confusion matrix offline before you ever touch `claims.csv`. Concretely you can: (a) compute exact-match accuracy for the 6 enum columns + boolean columns and multi-label F1 for `risk_flags`; (b) detect systematic biases (e.g., over-predicting `supported`, under-flagging `manual_review_required`); (c) tune the `evidence_standard_met` / `valid_image` decision thresholds against the 18:2 skew; (d) verify the `issue_type=none`/`unknown` rule on the 5 rows that use them; (e) confirm `supporting_image_ids` subset-selection logic on case_001/case_007/case_020. The sample's object balance (car 8 / laptop 6 / package 6) mirrors the test (car 18 / laptop 13 / package 13), so per-object calibration transfers. **Do not train/hardcode on the 20 rows** (README §What-you-need: "avoid hardcoded test labels") — use them only as an eval/calibration harness.

## 3. Old → New Transferable-Pattern Mapping

The prior solution is a 5-agent support-triage RAG pipeline (`RouterAgent → TriageAgent → ResponderAgent ↔ CriticAgent → FormatterAgent`) with typed shared state, model routing by cognitive load, an offline hybrid index, and a deterministic formatter. Almost every architectural decision transfers; the **retrieval/RAG stack is the main piece that does NOT** (the new task has no text corpus to retrieve — the "context" is images + 3 small CSVs that fit in-prompt).

| # | Old pattern (where it lives) | One-line reuse/adaptation for Multi-Modal Evidence Review |
|---|---|---|
| 1 | **Typed shared state `TicketState`** (`domain/types.py`) — one dataclass flows through pipeline, each agent reads/writes only its fields | Rename to `ClaimState`: fields for the 4 inputs + each of the 10 produced columns + `images: list[ImageRef]`, `history: UserHistory`, `evidence_req: str`; same scoped-read/scoped-write discipline keeps token cost flat. |
| 2 | **`domain/enums.py` — all constrained values as Enums, never string literals** | Define `ClaimStatus`, `IssueType`, `Severity`, `RiskFlag`, and three object-part enums (`CarPart`, `LaptopPart`, `PackagePart`); every model output passes through an enum parser that clamps to `unknown`/`none` on miss → eliminates trap-checklist items 6–11, 14. |
| 3 | **`TicketOutput` dataclass + deterministic `FormatterAgent` (no LLM)** mapping state → exact CSV columns (`agents/formatter.py`) | Becomes the `RowFormatter`: assembles the 14 columns, enforces order, lowercases booleans, joins `risk_flags`/`supporting_image_ids` with `;`, applies the `none`↔NEI rule — the single choke point that guarantees a schema-valid CSV. |
| 4 | **Model routing by cognitive load** (LOW/MEDIUM/HIGH tiers, `config.py` + `PipelineFactory`) | Route a cheap text-LLM for claim-extraction/history-flagging (LOW) and a **VLM** for image inspection (the new MEDIUM/HIGH tier); escalate to a stronger VLM only on ambiguous/contradiction-suspect rows → controls the cost line the eval report demands. |
| 5 | **Two-gate Router+Critic feedback loop** (`pipeline.py` loop, `CriticAgent` 3-axis scoring, hard retry cap) | Reuse as: **Gate-1 Triage** (extract claim, pick relevant images, set deterministic history flags, cheap injection screen) → VLM judgment → **Gate-2 Critic** that re-checks the VLM verdict against `evidence_requirements.csv` and enum legality, forcing `not_enough_information`/`manual_review_required` when grounding is weak. Same `max_calls` cap. |
| 6 | **Structured-output discipline** — `_parse_json` strips `<thinking>`/fences, first-JSON-object extraction (`agents/base.py`) | Reuse verbatim for the VLM: force a single JSON object with the 10 produced fields; the existing fence/thinking-stripper handles VLMs that wrap JSON in prose. Add per-field enum validation on top. |
| 7 | **Pattern B / Pattern C prompt structures** (Role+Situation+Mission+Guardrails+Format; +forced `<thinking>`) — `CONTEXT.md` AD-6, `prompts/*.md` | VLM "judge" prompt = Pattern C (force `<thinking>` describing what is literally visible per image **before** committing enums) → improves grounding and gives the justification text for free; the Formatter is Pattern B (deterministic). |
| 8 | **Universal security guardrail vs prompt injection** — token-free regex pre-gate (`router.py` `_INJECTION_PATTERNS`) + "ticket text is untrusted" in every prompt | Directly needed: 7 test rows contain approve/ignore/instruction language. Reuse the regex pre-gate on `user_claim`, and add the multimodal twist — instruct the VLM to ignore text **rendered inside images** and instead emit `text_instruction_present`; never let it flip `claim_status`. |
| 9 | **Deterministic offline index / "build once, load fast"** (`index/`, ADR-0005) | Repurpose the spirit: pre-load and cache `user_history.csv` + `evidence_requirements.csv` into in-memory dicts keyed by `user_id` and `(object,issue_family)`; cache VLM results by image hash so re-runs and shared images cost nothing → feeds the caching/throttling section of the eval report. |
| 10 | **Evaluation rigor** — eval harness vs labeled samples, custom rubric, honest overfitting disclaimer (`docs/optimization-log.md`, `scripts/evaluate.py`) | Reuse the harness shape: score the 10 produced columns against `sample_claims.csv` (exact-match for enums/booleans, F1 for `risk_flags`), keep the "this is a small set, don't overfit" honesty, and compare ≥2 strategies (see §4). This is now a **hard submission requirement**, not optional. |
| 11 | **Env-var-only secrets + typed `config.py` singleton** (no scattered `os.getenv`, frozen `Settings`) | Reuse as-is; swap `GEMINI_API_KEY` for `OPENAI_API_KEY`/`ANTHROPIC_API_KEY` per new AGENTS §6.2; keep one frozen settings object holding model names, paths, batch size, retry/throttle config. |
| 12 | **SOLID/DI composition root** (`PipelineFactory`, Protocols `LLMClient`/`Searcher`/`ContextCompressor`) | Keep DI: define a `VLMClient` Protocol so Anthropic/OpenAI/Gemini VLMs are swappable; drop the `Searcher`/`ContextCompressor` protocols (no RAG). One `ClaimPipelineFactory` wires VLM + formatter + history/req loaders. |
| 13 | **Canned escalation / safe-default responses** (`responder.py` constants) | Maps to safe defaults when the VLM can't decide: default to `not_enough_information` + `manual_review_required` + `supporting_image_ids=none` + `severity=unknown` rather than guessing `supported` — the conservative default that matches sample behavior. |

**Patterns that do NOT transfer:** the BM25 + semantic-rerank + LLMLingua retrieval stack (ADR-0001/0003), the committed `embeddings.npy`/`chunks.jsonl`/`bm25_corpus.txt` index, the `text-embedding`/`voyage` embedders, and the support-corpus contextual-chunk headers — there is no knowledge corpus to retrieve in this task. The `mcp_server.py` `triage_ticket` MCP contract and the `discover_models.py` provider plumbing are reusable scaffolding but not required by the new spec.

## 4. `evaluation/evaluation_report.md` — exact requirements checklist

**B. Strategy/model comparison (≥2 configurations — explicitly required)**
- [ ] Compare **at least two** of: different prompts, different VLM/model configs, or different strategies (e.g., single-pass VLM vs Triage→VLM→Critic two-gate; or VLM-only vs VLM+deterministic-history-flag post-processor; or two model tiers). README §Evaluation: "at least two strategies, prompts, or model configurations compared."
- [ ] Show the metric table side-by-side on `sample_claims.csv` for each strategy.
- [ ] State and justify **the final strategy chosen for `output.csv`** (README §Evaluation explicitly asks for "the final strategy used").

**C. Operational analysis (problem_statement §Operational analysis — every bullet required)**
- [ ] **Approximate number of model calls** for sample processing (20 rows) AND test processing (44 rows) — broken down by tier if multi-model.
- [ ] **Approximate input/output token usage** (per-call estimate + totals; images count toward input tokens — state how images are tokenized for your provider).
- [ ] **Number of images processed**: sample = 29, test = 82 (state these; 13 single-image / 24 two-image / 7 three-image test rows).
- [ ] **Approximate cost to process the full test set, with explicit pricing assumptions** (cite the per-MTok input/output and per-image price you assume for the chosen provider/model; show the arithmetic: calls × tokens × price + images × image-price).
- [ ] **Approximate latency / runtime** (per-claim and full-44-row wall-clock; note serial vs concurrent).
- [ ] **TPM/RPM considerations + batching / throttling / caching / retry strategy**: state assumed rate limits and how you stay under them — e.g. concurrency cap, exponential-backoff retry on 429 (the old `GeminiClientFactory` already has this), **caching VLM results by image hash** so the 24+7 multi-image rows and any repeated images aren't re-billed, and batching of the cheap history/requirement lookups (which are zero-LLM).
- [ ] A sentence acknowledging the spec's framing: "not expected to optimize perfectly, but must show consideration of cost, latency, rate limits, and avoidance of unnecessary repeated calls."

- [ ] Deterministic where possible; secrets from env vars only (`OPENAI_API_KEY`/`ANTHROPIC_API_KEY`), never hardcoded.
